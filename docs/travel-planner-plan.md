# 멀티 에이전트 여행 플래너 구현 계획

작성일·수정일: 2026-11-18 · 버전: 5 · 상태: 제품 요구사항 및 구현 계획 · 제출 마감: 2026-12-09(사용자 지정)

이 문서는 목표 설계입니다. 구현 완료를 의미하지 않으며, 실제 구현·검증 현황은 [구현 상태](implementation-status.md)와 구분합니다.

**조사 방식 변경 결정:** 공식 약관 대조 후 사용자 선택에 따라 Gemini는 계획·검토에 유지하고, 사실 근거는 저장·재배포가 허용된 공개 자료로 전환합니다. HTML 가이드북 요구를 유지하며 Wikivoyage 본문 조회와 출처·라이선스 처리를 연결했습니다. 실제 모델의 문서 선택·추천 품질과 공개 배포 검증은 남아 있습니다. 상세 근거는 [조사 자료 정책](source-policy.md)에 기록합니다.

### 제품 목적과 완료 판단

이 프로젝트의 멀티 에이전트는 **사용자의 여행을 계획하는 제품 내부의 AI 역할들**입니다. 사용자가 자신의 취향·여행 조건·API 키를 입력하면, 역할별 조사와 검토를 거쳐 여행 중 읽을 수 있는 HTML 가이드북을 만드는 것이 핵심입니다. 제작자 개인의 실제 사용을 먼저 검증하되, 공개 웹앱에서는 방문자마다 독립적인 조건과 키를 사용합니다.

| 핵심 요구 | 설계 및 확인 기준 |
|---|---|
| 개인화 | 취향 원문과 피하고 싶은 활동을 유지하고, 추천마다 반영한 조건을 설명합니다. 동일 여행 조건에서 취향만 바꾼 결과를 비교합니다. |
| 실제 멀티 에이전트 실행 | 역할별 입력·결과가 다음 작업에 전달되고, 검토 결과가 제한된 수정 작업으로 이어지는지 확인합니다. 진행 애니메이션만으로 실행을 증명하지 않습니다. |
| 개인 API 키 | 각 사용자의 키로 실제 생성하며, 새로고침 후 키가 남지 않고 저장 데이터·HTML·로그에도 포함되지 않는지 확인합니다. |
| 가이드북 완결성 | 일정뿐 아니라 추천 이유, 이동, 식사·숙박, 비용 상태, 대안, 출처를 연결합니다. 확인되지 않은 정보를 채워 완성된 것처럼 보이게 하지 않습니다. |
| 공개 이용 | 키 없이 예시 열람·편집·다운로드가 가능하고, 본인 키를 넣으면 실제 생성으로 이어지는지 배포 환경에서 각각 확인합니다. |
| 휴대성 | 단일 HTML을 네트워크 차단 상태와 모바일 화면에서 열고 본문·목차·인쇄 레이아웃을 확인합니다. 외부 링크 조회는 온라인 기능으로 구분합니다. |

### 범위 조정의 원칙

- **우선 반영:** 가이드북 중심 화면·데이터 구조, 취향 역질문, 관광·식당·숙박 조사, 키 없는 예시 두 유형, 단계별 실행, 실제 수정 증거 보존.
- **조건부 적용:** 외부 조사 서비스의 언어·모델·지역 지원과 출처 표시·저장 조건은 공식 문서와 실제 계정으로 확인한 범위에서 적용합니다. 검토 자료의 요금·한도 수치를 검증 없이 확정 요구사항으로 복사하지 않습니다.
- **유지할 선택:** 서버 경유의 단계별 호출을 사용합니다. 브라우저 직접 호출은 대안으로 남기되, 이번 범위에서는 공통 입력 검증과 오류·실행 한도 관리에 집중합니다.
- **후속 확장:** 공개 공유 링크, 과거 버전 복원 UI, 자동 환율, 내장 지도, 여러 AI 제공사 지원. 로그인만으로 가이드북을 공개하지 않습니다.
- **제출 핵심에 포함:** 실제 개인 키 연결은 생성 기능에 필수이므로 DB 가산점 단계까지 미루지 않습니다. 확정 예약 보호 역시 고급 편집과 관계없이 처음부터 적용합니다.

기능을 단계적으로 구현해도 핵심 결과물의 품질을 낮추지는 않습니다. 가이드북 생성·수정·내보내기와 공개 이용 흐름을 먼저 완성하고, 확장 기능은 이 흐름이 검증된 뒤 추가합니다.

### 핵심 설계 결정

| 쟁점 | 결정 | 이유 |
|---|---|---|
| 핵심 결과물 | 취향과 여행 조건을 반영한 단일 HTML 가이드북 | 여행 중 읽고 보관할 수 있는 결과물을 중심으로 화면과 데이터를 설계 |
| 개인 사용과 공개 서비스 | 제작자의 실제 사용을 우선 검증하고, 다른 사용자도 본인 키로 생성 | 개인 취향을 기본값으로 강제하지 않고 사용자별 조건으로 추천 |
| 생성 순서 | 조건 확인 → 거점·숙박 일수 승인 → 조사·일정·예산 → 설명 작성·검토 → 출력 | 원하지 않는 도시 구성으로 상세 생성을 진행하는 낭비 방지 |
| 제출 우선순위 | 가이드북 생성·편집·다운로드·모바일·공개 배포 우선, 계정 저장과 고급 편집은 단계적 추가 | 핵심 흐름의 완성도를 먼저 확보 |
| 키 없는 체험 | 두 유형의 예시 열람·수정·HTML 다운로드, 명시적인 진행 예시 | 키 발급 전에도 대상과 쓸모를 확인 |
| 실행 위치 | 브라우저에서 진행 상태 관리, 서버에서 단계별 AI 호출 | 공통 입력 검증·오류 처리·요청 제한 유지; 긴 요청은 도시·날짜 단위 분할 |
| 초기 AI 제공사 | Gemini 우선, 다중 제공사는 후속 확장 | 조사 도구와 출처 처리의 검증 범위를 관리 |
| 공유 범위 | 파일 다운로드 우선, 공개 공유 URL은 후속 확장 | 개인 여행 계획이 의도 없이 공개되는 상황 방지 |

## 1. 제품 방향과 범위

**“내 취향과 여행 조건을 입력하면 여러 AI 에이전트가 나만의 HTML 여행 가이드북을 만들어 주는 시스템”을 공개 반응형 웹앱으로 만듭니다.**

우선 제작자 본인이 실제 여행에 활용할 수 있는 품질을 목표로 하며, 배포 후 다른 여행자도 각자의 API 키로 사용할 수 있게 합니다. 웹앱의 입력·협의·편집 화면은 제작 도구이고, 핵심 결과물은 여행 중 휴대전화로 읽거나 파일로 보관할 수 있는 **가이드북 형태의 여행 계획표**입니다. 단순한 장소 나열보다 취향에 맞는 추천 이유, 실행 가능한 이동·휴식, 현지 이야기와 대안을 함께 제공합니다.

대상은 취향이 뚜렷한 해외 자유여행자입니다. 국가·도시를 이미 정한 사람과, 국가만 정하고 도시 추천부터 필요한 사람을 모두 지원합니다.

사용자는 기본 조건을 입력하고, AI가 제안한 **숙박 거점·도시별 체류일·근교 방문 구성**을 먼저 확인합니다. 이 구성을 확정한 후 상세 일정을 생성합니다. 여행 기간만으로 도시 수를 자동 확정하지 않습니다.

**첫 제출 버전에 포함할 기능**

- 해외 국가와 도시 선택, 취향 기반 도시 추천.
- 단일 도시·근교 당일치기·여러 도시 이동 여행.
- 숙박을 포함한 현지 예산 계획.
- 장소 조사, 일정 생성, 검토, 부분 재생성.
- 한국어 가이드북 미리보기, CSS를 내장한 단일 HTML 다운로드, 인쇄/PDF 저장용 스타일.
- 관광·식당·숙박 지역 추천과 현지 설명, 준비·재확인 목록.
- 브라우저 초안 보관·불러오기. 계정 저장과 부분 재생성은 아래 단계별 일정으로 추가합니다.
- 사용자 본인의 Gemini API 키를 사용하는 방식.

항공·숙소 예약, 결제, 실시간 공동 편집, 전 세계 교통편의 예약 가능 여부 보장은 제외합니다. 항공 일정이나 예약한 숙소는 사용자가 입력하여 제약 조건으로 반영할 수 있습니다.

## 2. 핵심 기능과 화면 구성

### 여행 시작 화면

앱의 대상과 쓸모를 짧게 설명하고, **새 여행 만들기 / 예시 여행 둘러보기 / 내 여행**을 제공합니다.

API 키가 없어도 명확히 표시된 예시 여행을 볼 수 있습니다. 실제 AI 생성에는 본인 키가 필요하며, 예시 실행을 실제 API 실행처럼 표시하지 않습니다.

예시는 단일 거점·근교형과 다중 도시형을 각각 제공합니다. 키 없이 가이드북 열람·HTML 다운로드와 로컬 일정 편집을 체험할 수 있습니다. 진행 화면은 별도 **예시 재생** 표시를 붙이며, AI 재생성 버튼은 키 입력으로 안내합니다. 공개 예시에는 실제 개인 예약·여행자 정보를 넣지 않습니다.

### 여행 조건 입력 화면

여러 단계로 나누되 이전 단계로 돌아가도 입력을 보존합니다.

| 단계 | 입력 내용 |
|---|---|
| 목적지 | 국가, 방문 희망 도시, 도시 추천 필요 여부, 꼭 방문할 장소 |
| 일정 | 출발·종료 날짜, 현지 도착·출발 시간, 확정된 이동 일정 |
| 동행·예산 | 인원, 일행 전체의 현지 총예산, 기준 통화, 숙박 수준 |
| 취향 | 음식·문화·자연·쇼핑 등의 우선순위, 피하고 싶은 활동 |
| 여행 방식 | 여유·보통·빡빡한 일정, 도보 허용 정도, 선호 교통수단, 숙소 이동 선호 |
| 확정 사항 | 예약한 숙소·행사·교통편과 변경할 수 없는 일정 |

날짜로 여행 일수를 계산하고, 예산이 **일행 전체 금액이며 항공료는 제외**라는 점을 명시합니다. 숙박 객실 수를 입력받아 인원 수와 숙박비를 단순히 곱하는 오류를 방지합니다.

취향은 태그뿐 아니라 자유 서술로 받습니다. 좋아했던 여행 경험, 꼭 하고 싶은 일, 음식 기호·피하는 음식, 붐비는 곳에 대한 선호, 하루 활동 시작 시간과 휴식 빈도를 선택 입력으로 둡니다. 필수 입력은 목적지·기간·인원·예산·여행 속도·확정 예약 여부로 제한하고, 결과를 바꾸는 중요한 불확실성만 묶어서 역질문합니다. 추천 항목은 어떤 취향·조건을 반영했는지 설명하며, 근거 없는 개인 특성을 추론하지 않습니다.

### 여행 골격 협의 화면

상세 일정 전에 다음을 먼저 제안합니다.

- 숙박 거점과 도시별 숙박 일수.
- 도시 사이의 이동일.
- 각 거점에서 가능한 근교 방문 후보.
- 대략적인 예산 배분과 확인이 필요한 정보.
- 사용자가 결정해야 하는 질문.

예를 들어 히로시마를 숙박 거점으로 두고 미야지마·오노미치를 각각 당일치기로 제안하거나, 이스탄불·카파도키아·안탈리아의 숙박 구간과 이동일을 나누는 형태입니다. **실제 방문 가능성과 적정 배분은 조회 결과와 사용자 답변으로 결정합니다.**

사용자는 도시 추가·삭제, 숙박 일수 변경, 방문지 고정을 할 수 있습니다. 승인되지 않은 도시 이동을 상세 일정 생성 과정에서 임의로 추가하지 않습니다.

### 여행 편집 화면 — 가이드북 제작 작업 공간

```text
여행 제목 · 기간 · 총예산              가이드북 보기 / 저장

[숙박 거점·날짜 목록] [선택한 날짜의 일정] [장소·이동 정보]
 히로시마             오전 방문지         장소 출처
 ├ 첫째 날            점심·휴식           지도 열기
 ├ 둘째 날            오후 방문지         이동 확인
 └ 셋째 날            저녁               예상 비용

[검토 결과: 예산·이동·일정 충돌·확인 필요]

[수정 요청: “둘째 날은 걷는 시간을 줄여 주세요”]
```

일정 카드에는 시간, 장소, 추천 이유, 예상 비용, 이동 정보, 출처를 표시합니다.

편집 동작은 다음과 같이 단계적으로 제공합니다. 1단계는 장소 삭제·시간·메모 수동 수정과 가이드북 다시 렌더링, 3단계는 고급 AI 편집을 제공합니다.

- 장소 추가·삭제·교체, 순서 및 체류 시간 변경.
- 특정 장소·시간·날짜 고정.
- 하루 또는 선택한 구간만 다시 생성.
- 변경 전후 비교와 적용·취소.
- 적용된 수정의 이유. 이전 버전 복원 UI는 후속 확장입니다.

고정 일정과 새로운 요청이 충돌하면 자동으로 고정을 해제하지 않고 선택을 요청합니다.

확정 예약과 필수 방문지는 1단계부터 보호하며, 임의 항목을 고정하는 UI와 하루 단위 AI 재생성은 3단계에서 추가합니다. 변경한 일정이 가이드북과 다를 경우 '가이드북 갱신 필요'를 표시하고, 현재 버전으로 다시 렌더링한 뒤 다운로드합니다.

초기 버전의 지도 기능은 **도시·장소별 Google Maps 링크와 이동 구간 요약**으로 제공합니다. 앱 내부의 인터랙티브 지도와 실시간 경로 렌더링은 후속 확장으로 분리하여, 별도 지도 키 없이 핵심 기능을 사용할 수 있게 합니다.

### 예산·검토 화면

숙박·식비·관광·현지 이동별 예상 비용과 잔여 예산을 제공합니다.

- 확인된 가격, 사용자가 입력한 금액, 계획용 추정치를 구분합니다.
- 금액을 모르는 항목을 0원으로 처리하지 않습니다.
- 통화 변환에는 적용 환율·출처·시점을 표시합니다.
- 확인된 환율이 없으면 사용자가 환율을 입력하며, 자동 환산을 확정값처럼 표시하지 않습니다.
- 예산 초과 시 줄일 수 있는 항목과 일정 대안을 제안합니다.

### 내 여행·설정 화면

- 여행 목록, 복제·삭제, 최신 저장본 불러오기. 과거 버전 복원 화면은 후속 확장.
- Gemini 키 입력·연결 확인·삭제.
- 로그인과 로그아웃.
- JSON 내보내기·가져오기와 인쇄용 화면.

### 가이드북 보기 / HTML 내보내기 — 핵심 결과물

가이드북은 웹앱과 동일한 검증된 여행 데이터를 사용하며, 별도의 AI 호출 없이 HTML로 렌더링합니다. 일자·도시·정보 섹션을 접고 펼치는 목차와 날짜 바로가기를 제공합니다.

| 구성 | 담을 내용 |
|---|---|
| 표지 | 여행 제목, 기간, 도시, 여행 테마와 취향 요약 |
| 한눈에 보기 | 숙박 거점, 도시별 체류, 이동일, 전체 일정 요약 |
| 날짜별 여행 | 시간표, 관광·식사·휴식, 추천 이유, 이동·환승 안내, 비용, 우천·피로 시 대안 |
| 장소 이야기 | 해당 장소를 즐기는 관점, 확인된 역사·문화 배경, 체류 팁 |
| 식당·숙박 | 끼니별 주 후보와 대안, 숙박하기 좋은 지역과 선택 이유, 확인 가능한 숙소 후보 |
| 예산 | 항목별 합계, 미확인 금액, 추정·입력·조회 금액 구분 |
| 준비·현지 안내 | 준비물, 교통 이용 팁, 예절·현지어, 출발 전 확인할 항목 |
| 근거·상태 | 내용별 출처·확인 시점, 미확인 사항, 생성일과 여행 버전 |

식당은 음식 기호·동선에 맞는 주 후보와 대안을 조사하며, 자료가 부족하면 개수를 억지로 채우지 않습니다. 숙박은 거점마다 동네 후보와 장단점을 우선 제안하고 필요 시 숙소 후보를 붙입니다. 가격은 조회 조건과 시점을 표시하며 실시간 예약 가능 여부를 보장하지 않습니다. 사용자 입력 항공·숙박 시간은 첫날·마지막 날 및 체크인 일정을 제한합니다.

현지 설명은 출처가 있는 사실만 작성하고, 확인되지 않은 운영시간·휴무·가격을 채우지 않습니다. 입국·비자 등 변동이 크고 개인 조건에 좌우되는 내용은 공식 확인 링크와 확인 필요 표시를 우선 제공합니다.

**HTML 출력 계약**

- 단일 `.html` 파일에 본문과 CSS를 포함하고 시스템 글꼴 및 기본 HTML 접기/펼치기를 사용합니다. 인터넷 없이 본문·목차·레이아웃을 읽을 수 있게 합니다.
- 외부 지도·출처·예약 사이트 링크는 온라인 연결이 필요하다고 표시합니다. 오프라인 열람과 실시간 정보 조회를 구분합니다.
- 사진은 필수 요소로 두지 않습니다. 사용·재배포 권한과 출처를 확인한 자료만 포함하고, 외부 이미지가 로드되지 않아도 본문을 읽을 수 있게 합니다.
- 인쇄 시 접힌 본문을 모두 펼치고 탐색 UI를 숨깁니다. 브라우저 인쇄의 PDF 저장을 지원하며 별도 PDF 생성 서버는 두지 않습니다.
- LLM이 만든 임의 HTML·스크립트를 실행하지 않습니다. Zod로 검증한 데이터와 신뢰된 템플릿을 사용하고 텍스트 이스케이프·URL 허용 목록을 적용합니다.
- API 키·로그인 토큰·예약 관리 코드·원문 대화는 포함하지 않습니다. 내보내기 전에 개인 메모·숙소 주소 등 포함 항목을 확인할 수 있게 합니다.
- 내용별 출처를 본문 가까이에 유지하고 마지막에 출처 목록도 제공합니다. 출처 제공사의 저장·표시·재배포 조건을 확인한 데이터만 내보냅니다. 허용 여부가 확인되지 않은 외부 원문·사진은 제외하고 링크로 대체합니다.
- 일정 충돌이 남으면 **초안**, 중요한 정보가 미확인이면 **확인 필요**로 표시하여 다운로드할 수 있게 합니다. '검토 완료'는 수행한 검사 범위만 의미하며 실제 영업·운행을 보증하지 않습니다.
- 공개 공유 URL은 후속 확장으로 분리합니다. 로그인이나 가이드북 생성만으로 여행 내용을 공개하지 않습니다.

모바일에서는 날짜 탐색을 상단에 두고 **일정 / 장소·이동 / 예산·검토** 탭으로 전환합니다. 키 입력과 수정 요청은 별도 패널로 열어 좁은 화면에서 일정이 가려지지 않게 합니다.

디자인 초안은 따뜻한 밝은 배경, 짙은 청록색, 제한적인 강조색을 사용하는 여행 노트형 화면으로 제안합니다. 도시·날짜·고정 상태를 색상만으로 구분하지 않고 텍스트와 아이콘을 함께 사용합니다.

## 3. 에이전트 구조와 기술 스택

### 에이전트의 실제 역할

| 역할 | 책임 | 결과 |
|---|---|---|
| 총괄 에이전트 | 조건 해석, 추가 질문, 작업 분배, 도시 구성 협의 | 승인할 여행 골격과 다음 작업 |
| 장소 조사 에이전트 | 취향에 맞는 장소 조사와 출처 수집 | 근거가 연결된 장소 후보 |
| 일정·이동 에이전트 | 거점·근교·도시간 이동과 일별 일정 구성 | 시간표와 이동 구간 |
| 예산 에이전트 | 비용 분류, 예산 초과 분석, 대안 제안 | 예산표와 조정안 |
| 검토 에이전트 | 제약 위반·근거 부족·과밀 일정 점검 | 수정 요청 또는 검토 완료 결과 |
| 가이드북 큐레이터 | 검증된 일정·취향을 바탕으로 장소 설명·현지 팁을 조사·편집 | 출처가 연결된 한국어 가이드북 콘텐츠 |

각 역할은 독립된 지시문과 구조화된 입출력을 사용합니다. 총괄은 질문·조사·수정 중 필요한 다음 작업을 선택합니다. 단순히 같은 응답에 역할 이름만 붙이지 않습니다.

실행 흐름은 **조건·취향 확인 → 여행 골격 승인 → 관광·식당·숙박 조사 → 상세 일정·예산 구성 → 가이드북 콘텐츠 작성 → 검토 → 필요한 수정 → HTML 렌더링·사용자 확인**입니다. 자동 수정은 실행당 최대 두 차례로 제한하고, 해결되지 않은 문제는 사용자에게 표시합니다. 큐레이터가 추가한 사실도 최종 검토 범위에 포함합니다. 식당·숙소 조사는 장소 조사 역할 내부의 별도 작업으로 구성하여 독립 에이전트 수를 과도하게 늘리지 않습니다.

시간 겹침·일수 합계·금액 합계·고정 항목 보존은 코드로 검사합니다. LLM 검토만으로 정확성을 보장한다고 표시하지 않습니다. 이 구성은 공식 문서의 총괄–작업자 및 평가–개선 패턴을 참고합니다. [Anthropic 설계 문서](https://www.anthropic.com/engineering/building-effective-agents)

### 기술 스택

| 영역 | 선택 | 적용 방식 |
|---|---|---|
| 웹·서버 | Next.js App Router + TypeScript | 화면과 서버 API를 하나의 프로젝트에서 관리 |
| UI | Tailwind CSS + Radix UI | 접근 가능한 기본 동작에 맞춤 시각 디자인 적용 |
| 입력·검증 | React Hook Form + Zod | 폼 입력과 에이전트 결과 검증 |
| AI | Google Gen AI SDK + Gemini | 사용자 키로 역할별 호출, 도구 사용 |
| 장소 근거 | Wikivoyage MediaWiki API | 실제 여행 안내 본문·문서 버전 조회, CC BY-SA 4.0 출처 표시 |
| 조사 대상 선택 | Gemini 구조화 출력 | 승인된 거점과 근교의 영문 문서명 선택; 누락 자료를 모델 지식으로 채우지 않음 |
| 가이드북 출력 | React 기반 정적 HTML 템플릿 + 내장 CSS | 검증 데이터로 미리보기·단일 HTML·인쇄 화면 생성 |
| 실행 제어 | TypeScript 상태 머신 | 역할별 실행, 중단, 재시도, 사용자 승인 관리 |
| DB·인증 | Supabase PostgreSQL + Auth | 이메일 로그인, 사용자별 여행·버전 저장 |
| 배포 | Vercel | Next.js 웹앱과 서버 API 배포 |
| 검증 | Vitest + Playwright | 계산·제약 검사 및 실제 사용자 흐름 |
| 영상 | Remotion | 과정 영상과 트레일러를 코드로 제작 |

Next.js 서버 Route Handler와 MediaWiki API를 사용합니다. 실제 작동을 검증한 Gemini 모델과 의존성 버전을 관리합니다. [Next.js](https://nextjs.org/docs/app/api-reference/file-conventions/route), [MediaWiki API](https://www.mediawiki.org/wiki/API:Revisions)

공개 여행 안내 본문을 현재 교통 시간표나 예약 가능한 운임으로 간주하지 않습니다. 확인되지 않은 이동 시간·운임은 추정 또는 확인 필요로 표시하고 외부 확인 링크를 제공합니다.

### 조사 언어·출처·실행 제약

영문 Wikivoyage 여행 안내 본문을 실제 조회하고 한국어로 번역·요약합니다. 문서명 선택에는 국가·거점을 함께 사용하고, 원문의 지역이 여행 조건과 불일치하면 사용하지 않도록 합니다. 현지·영문 명칭을 보존하며 번역하면서 출처 연결을 잃지 않게 합니다. 문서 선택 정확성은 실제 생성에서 추가 검증합니다.

문서가 없으면 자료 부족 상태를 남기며 업체·가격을 만들어 채우지 않습니다. 조회 서비스가 실패하면 완료한 거점의 자료를 보존하고 명시적으로 재시도합니다. 다른 외부 사이트를 자동 수집하는 대체 경로는 두지 않습니다. 자료의 이용 조건을 검증한 어댑터만 추가합니다.

출처 이름·원문 URL을 해당 내용 가까이에 연결합니다. 원문 버전·수정 시점·기여자 이력 링크와 CC BY-SA 4.0, 번역·재구성 표시를 저장본과 HTML 모두에 유지합니다. 자료 기반 안내 본문을 공유·변형할 때 동일조건 배포 요건이 있음을 내보내기 전에 안내합니다. 개인 예약정보를 공개한다는 뜻은 아니며 사진은 별도 검증 전 포함하지 않습니다. [Wikivoyage 이용 조건](https://en.wikivoyage.org/wiki/Wikivoyage:Copyleft)

실행은 **서버 경유 + 단계별 요청**을 유지합니다. 입력 검증·공통 오류 처리·실행 한도 관리가 일관되고 브라우저 직접 호출의 지원·보안 검증을 별도로 늘리지 않기 때문입니다. 긴 여행은 도시·날짜 단위로 나누고 완료된 단위를 재사용합니다. Vercel 공식 문서의 Fluid compute Hobby 함수 최대 시간은 조회 시점에 300초이며 스트리밍도 제한에 포함됩니다. 실제 프로젝트 설정을 재검증하고 요청별 중단 시간을 그 한도보다 짧게 설정합니다. [Vercel 함수 제한](https://vercel.com/docs/functions/limitations)

### 데이터와 API

핵심 데이터는 `Trip`, `TripRevision`, `AgentRun`, `GuidebookExport`로 구성합니다.

- 여행에는 입력 조건, 숙박 거점, 일별 활동, 도시 간 이동, 예산, 출처, 고정 항목을 포함합니다.
- 적용된 수정은 새 버전으로 보존합니다.
- `GuidebookExport`는 여행 버전 ID·생성 시점·템플릿 버전·포함 항목·검토 상태와 출력용 스냅샷을 연결합니다. 출처별 보관 제한이 있는 데이터는 영구 스냅샷 대상에서 제외하거나 허용 기한을 적용합니다.
- 실행 기록에는 역할·상태·처리 결과 요약을 보관하고 API 키와 원문 요청 전체를 저장하지 않습니다.

주요 서버 인터페이스는 다음으로 제한합니다.

- 키 연결 확인.
- 도시 추천·여행 골격 생성.
- 승인된 골격의 상세 일정 생성.
- 선택 구간 수정·재검토.
- 로그인 사용자의 여행·버전 저장과 조회.
- 현재 여행 버전의 가이드북 미리보기·HTML 다운로드. 클라이언트에서 동일한 출력 템플릿으로 생성하며 별도 LLM 호출을 하지 않습니다.

오래 걸리는 작업은 단계별 요청으로 나누고 진행 이벤트를 전송합니다. 새로고침이나 중단 후에는 완료된 결과를 유지하고 키를 다시 입력하여 명시적으로 이어갑니다. 실패 시 무제한 자동 재호출하지 않습니다.

### 사용자 키와 저장 원칙

- Gemini 키는 브라우저 메모리에만 유지합니다. 새로고침·종료 시 재입력이 기본입니다.
- API 실행 시 HTTPS로 앱 서버에 전달하고, 서버는 해당 요청 처리에만 사용합니다.
- 키가 서버를 경유한다는 사실을 입력 화면에 안내합니다.
- 키를 URL, DB, 브라우저 영구 저장소, 분석 도구, 오류 로그에 기록하지 않습니다.
- 서버 공용 Gemini 키로 대체하는 기능을 두지 않습니다.
- `.env` 계열의 실제 비밀값은 Git 추적에서 제외하고 예시 파일에는 자리표시자만 둡니다.

Google 공식 문서에서도 Gemini API 인증에 키가 필요함을 확인했습니다. 실제 키 유형과 제한 설정은 연결 검증에 반영합니다. [Gemini API 키 문서](https://ai.google.dev/gemini-api/docs/api-key)

로그인 전 여행 초안은 현재 브라우저에 보관하고, 이메일 로그인 후 사용자가 저장을 선택하면 DB로 옮깁니다. 다른 사용자의 여행을 읽거나 수정하지 못하도록 DB의 행 수준 보안 정책을 적용합니다. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)

공개 사용자 대상 이메일 로그인에는 별도 SMTP 설정을 배포 조건으로 둡니다. 조회한 공식 문서상 기본 SMTP는 프로젝트 팀에 속하지 않는 주소로 발송을 제한하므로, 기본 설정만으로 일반 사용자가 로그인할 수 있다고 가정하지 않습니다. 발송 한도·수신·스팸함·만료 링크·배포 도메인 복귀를 실제 환경에서 검증합니다. Google 로그인은 SMTP 운영 부담을 비교할 대안이며, 제공사 설정을 검증한 뒤 채택합니다. 인증 설정 전에도 예시 열람과 로컬 가이드북 제작은 사용할 수 있게 합니다. [Supabase SMTP 공식 문서](https://supabase.com/docs/guides/auth/auth-smtp)

**개인 키 방식은 AI 호출 비용을 사용자별로 분리하지만, 배포 서버·DB 운영비까지 없애지는 않습니다.** 공개 배포에는 요청 빈도·동시 실행·입력 크기 제한을 적용합니다.

## 4. 검증 기준과 과제 제출 계획

### 필수 검증 시나리오

- 취향 입력을 바꿨을 때 추천 내용과 추천 이유가 달라지고, 피하는 음식·활동과 확정 일정이 지켜집니다.
- 키 없는 방문자가 두 유형의 예시 가이드북을 열고 HTML을 다운로드할 수 있습니다.
- 다운로드한 HTML이 네트워크 차단 상태에서 목차·본문·접기/펼치기를 유지하고, 모바일 및 인쇄 화면이 잘리지 않습니다.
- 일정 수정 후 가이드북 버전이 갱신되고, 내보낸 파일에 API 키·인증값·예약 관리 코드가 없습니다.
- 가이드북의 장소 설명·가격·운영시간과 출처 연결이 유지되며 원문·기여자·라이선스·변경 표시와 미확인 상태가 누락되지 않습니다.
- 악성 태그·스크립트·위험 URL을 포함한 모의 AI 응답이 HTML에서 실행되지 않습니다.

- 국가만 입력하면 도시 후보를 추천하고, 사용자가 확정한 뒤 상세 일정을 만듭니다.
- 한 거점에서 여러 근교를 방문하는 여행과 여러 숙박 도시를 이동하는 여행을 모두 처리합니다.
- 도착·출발 시간, 숙박 일수, 이동일을 반영합니다.
- 특정 일정을 고정하고 재생성해도 고정 내용이 유지됩니다.
- 예산 부족, 일정 충돌, 장소 정보 부족을 감추지 않습니다.
- 잘못된 키·권한 부족·할당량 초과·네트워크 실패 시 입력과 완료 결과를 보존합니다.
- 로그인 전 초안을 로그인 후 저장하고 다른 기기에서 불러옵니다.
- 사용자 간 DB 접근이 차단되며 키가 저장·로그·빌드 산출물에 남지 않습니다.
- 모바일·키보드 조작·빈 화면·로딩·오류 상태를 검증합니다.
- 공개 배포에서 예시 보기와 본인 키를 통한 실제 생성 흐름을 각각 확인합니다.

### 수정 증거와 Git 기록 절차

1. 화면의 첫 구현이 실행 가능한 시점에 커밋과 데스크톱·모바일 화면을 남깁니다. 비밀정보·개인정보가 있는 상태는 먼저 제거합니다.
2. 수정 전 화면을 `docs/process/before/`, 수정 후 화면을 `docs/process/after/`에 동일한 식별자로 보존합니다.
3. 사용자 지시 원문·날짜·수정 의도·관련 커밋을 `docs/process/prompts.md`에 기록합니다. 공개할 수 없는 값은 명확한 마스킹 표기로 제외하며 지시를 꾸며내지 않습니다.
4. 같은 화면 크기·예시 데이터를 사용해 전후 차이를 비교하고 CHECKLIST.md 한 행과 과정 영상 장면으로 연결합니다.
5. 가이드북 타이포그래피·색상, 날짜별 정보 구조, 모바일 목차·탐색 등을 검토하되 실제 사용자 판단에 따른 변경만 수정 실적으로 기록합니다.

서로 다른 날짜의 실제 작업 커밋을 유지합니다. `commit --amend`, `rebase`, `push --force`, `push --force-with-lease`, squash merge 등 평가 대상 이력을 재작성하는 작업은 사용하지 않습니다. 날짜를 소급하거나 미래로 조작하지 않습니다. 작업일마다 한국 시간의 날짜 경계를 피해서 커밋·푸시하고 원격 반영 여부를 확인하되, 특정 시각이 과제의 의무 조건인 것처럼 제시하지 않습니다. 줄바꿈은 구현 초기 `.gitattributes`에서 LF로 통일하고 기존 파일의 내용 변경과 구분합니다.

`CHECKLIST.md`는 **축 / 항목 / AI가 처음 준 것 / 내가 바꾼 것 / 바꾼 이유** 구조로 작성합니다. 디자인 수정은 실제 발생한 변경을 최소 세 항목 기록하며, 평가를 위해 의도적으로 나쁜 초안을 만들거나 변경 이력을 꾸미지 않습니다.

`video` 폴더에는 Remotion 기반의 과정 영상과 트레일러 코드를 둡니다. 사용자 제공 과제 기준에 따라 과정 영상은 2~3분으로 실제 수정 전후 비교를 3번 이상 포함하고 이유·사용자 지시를 제시합니다. 트레일러는 30초~1분으로 취향 입력 → 에이전트 실행 → 완성된 가이드북과 모바일 열람을 보여줍니다. 공개 저장소·배포 주소, 두 영상, CHECKLIST.md를 패들릿에 제출합니다. [Remotion 공식 문서](https://www.remotion.dev/docs/)

이번 프로젝트에서 실제로 구현하고 변경한 제품 내용과 사용자님의 의도를 기록합니다.

## 5. 주요 판단과 남는 한계

- **여러 도시 지원은 복잡하지만 핵심 요구입니다.** 처음부터 숙박 거점과 이동 구간을 데이터에 포함하고, 예약 기능을 제외하여 범위를 관리합니다.
- **개인 API 키 입력은 사용 장벽이 있습니다.** 키 없이 볼 수 있는 예시 여행과 연결 안내를 제공하되, 실제 생성에 공용 키를 사용하지 않습니다.
- **세계 모든 도시의 데이터 품질은 같지 않습니다.** 입력 가능한 지역을 넓게 제공하되, 정보 부족을 명시하고 근거 없는 일정은 확정하지 않습니다.
- **가이드북의 내용과 휴대성을 우선합니다.** 제출 버전은 외부 지도 연결로 실제 장소 확인을 지원하며, 내부 지도 렌더링과 고급 편집은 가이드북 생성·열람 품질을 확보한 뒤 확장합니다.

제품의 일부 코드는 작성되어 있으나, 계획에 포함된 모든 기능의 구현과 공개 서비스 검증이 끝난 것은 아닙니다. 특히 실제 사용자 키의 생성 품질, 계정 저장·접근 제어, 공개 배포, 출처 데이터의 저장·재배포 조건은 별도 검증 대상입니다. 기술 문서의 지원 모델·요금·서비스 제한 등 변동 가능한 사항은 적용 시 재검증합니다. 확인하지 않은 요금을 고정 비용으로 안내하지 않습니다.
